Şekil 1 - Normalize gözlem sonuç dağılımın = 25

Ana mühendislik sonuçları

  1. Tip ayrımı korunmuştur. String, array, integer ve boolean değerleri sessizce birbirine dönüştürülmez. Issuer, subject, audience ve NumericDate alanları kendi sözleşmeleri içinde değerlendirilir.
  2. Bağlam tamlığı açıkça modellenmiştir. Tenant, application object, client ID, credential, issuer, subject matcher ve audience birlikte taşınmadığında bir federated identity seçimi tamamlanmış sayılmaz.
  3. Zaman kararı tek saatten üretilir. Expiration, not-before, issued-at, auth-time, nonce saklama ve skew kararları enjekte edilen aynı saate bağlıdır; sınır eşitlikleri testlerle sabitlenmiştir.
  4. Token exchange çokluluğu kaybolmaz. Tekil parametre tekrarları reddedilir; resource ve audience çokluluğu korunur; scope-target kartesyen ürünü eksikse karar kapanır.
  5. PAC ayrıştırma önce yapısal sınırları doğrular. Descriptor sayısı, çarpım, sekiz bayt hizalama, offset-plus-size, overlap, SID ve signature şekilleri doğrulanmadan typed buffer sunulmaz.
  6. dMSA işlemi yalnızca komut dönüşüyle sınıflandırılmaz. Migration state, reciprocal link, geçici ACL, enrollment, SPN/policy aktarımı, RWDC/RODC kaynağı ve restore digest birlikte incelenir.
  7. Cloud Kerberos kapısı kapalı varsayılanla çalışır. Disposable tenant ve joined Windows 11 client bağlamı olmadan dış istek oluşturulmaz; RWDC-local durum client line-of-sight yerine geçmez.
  8. Kanıt zinciri tekrar üretilebilirdir. Canonical JSONL ledger, kaynak manifestleri ve rapor, byte-level SHA-256 bağlarıyla birbirine bağlanmıştır.

En önemli yorum sınırı

Bir testin başarılı olması, Microsoft Entra veya Windows ürününün bütün olası dağıtımlarda aynı davranacağını kanıtlamaz. Başarı, yalnızca tanımlı oracle veya belirtilen Windows Server 2025 laboratuvar koşulunda invariyant testinin geçtiğini gösterir.

Formal yöntem

Spesifikasyondan çalıştırılabilir invariyanta

Metinsel gereksinimler typed predicates, explicit clocks, bounded arithmetic ve normalize neden kodlarına dönüştürülür.

İnvariyant şeması

Her katalog girdisi yedi zorunlu semantik taşır: benzersiz rule ID, source ID, kaynak bölümü, kısa normatif özet, evidence class, en az bir positive case ve negative ya da observe case. Source ID ayrıca başlık, revizyon ve HTTPS primary URL ile bağlanır.

Invariant := (id, source, revision, section, summary, evidence_class, cases)

Bu bağ, test adının tek başına normatif anlam taşıdığı varsayımını ortadan kaldırır. Test, ancak hangi kaynak bölümünü ve hangi karar sınıfını temsil ettiğiyle birlikte denetlenebilir.

Karar fonksiyonunun özellikleri

Deterministik

Aynı typed input, aynı injected clock, aynı policy profile ve aynı source revision aynı karar ve reason code üretir.

Fail-closed

Eksik alan, tip belirsizliği, bilinmeyen reason code veya karşılanmayan önkoşul başarıya normalize edilmez.

Bağlam korunumu

Tenant, application, issuer, subject, audience, actor ve target gibi eksenler birbirine karıştırılmaz.

Kanıt sınıfı korunumu

Bir local-adapter sonucu windows-observation veya hosted-service iddiasına otomatik yükseltilmez.

Sınır değer yaklaşımı

Zaman, uzunluk ve offset kararlarında yalnızca tipik geçerli örnekler kullanılmadı. Eşitlik noktaları, bir önceki ve bir sonraki değer, negatif sayılar, boolean-as-integer durumu, aşırı descriptor sayısı, misalignment, overlap, duplicate singleton ve repeated identifier durumları property testlerle kapsandı.

accepted_time := (nbf - skew) <= now <= (exp + skew) AND iat <= (now + future_tolerance)
contained_region := offset % 8 == 0 AND 0 < size <= limit AND offset <= total - size

İkinci ifade, offset + size toplamını doğrudan hesaplamadan önce offset <= total - size biçiminde kontrol ederek sabit-width aritmetik için overflow-safe bir sözleşme kurar.

Reason code disiplini

Serbest metin hata mesajları kanıt formatına taşınmaz. Her karar enum ile tanımlı, bounded ve lower-case bir reason code kullanır. Bu yaklaşım; dil, platform veya exception metni değişse bile evidence diff'lerinin semantik kalmasını sağlar.

Negatif test ile ürün etkisi arasındaki ayrım

Bir oracle'ın girdiyi reddetmesi, gerçek bir hizmetin aynı girdiyi kabul ettiği veya bu farkın güvenlik etkisi taşıdığı anlamına gelmez. Ürün davranışı bağımsız olarak gözlenmeden karşılaştırmalı sonuç kurulmaz.

OpenID Connect

Issuer, audience, nonce ve ortak zaman ekseni

ID token değerlendirmesi discovery issuer, registered client, sent nonce ve policy clock bağlamında yapılır.

OIDC karar sırası

  1. Issuer exact match: Discovered issuer identifier ile token iss değeri byte-level string semantiğinde karşılaştırılır; case veya trailing slash normalizasyonu yapılmaz.
  2. Audience membership: Registered client audience setinde bulunmalıdır. Ek audience varsa her ek değer explicit trusted set içinde olmalıdır.
  3. Nonce binding: Authorization request'te nonce gönderildiyse ID token aynı nonce'u taşır. Kabul edilen nonce local replay policy içinde tek kullanımlık tüketilir.
  4. Temporal consistency: exp, iat, isteğe bağlı auth_time, max_age ve nonce retention aynı injected clock'tan türetilir.

Audience invariant

client_id in aud AND (aud - trusted_audiences) == empty

Client bulunması tek başına yeterli değildir; bilinmeyen ek audience kararın kapanmasına neden olur.

Nonce invariant

sent_nonce != null => token_nonce == sent_nonce AND consume_once(sent_nonce)

Gönderilen nonce'un token'da olmaması, farklı olması veya daha önce tüketilmiş olması ayrı reason code üretir.

Zaman sınırları

Property testler expiration sınırının skew sonrası exclusivity davranışını, not-before sınırının inclusivity davranışını, far-past ve future issued-at durumlarını ve boolean NumericDate girdilerini kapsar. auth_time, yalnızca max_age talep edildiğinde typed ve policy-bound bir zorunluluğa dönüşür.

Deterministik nonce expiry

Nonce store duvar saatini doğrudan okumaz. Test clock ilerletildiğinde tam retention sınırında karar tekrar üretilebilir; test suite zamanlamaya bağlı bekleme kullanmaz.
